The Problem

The internet has a trust crisis. You can no longer look at a piece of text and know whether a person wrote it. AI detection tools try to solve this by analyzing the output — word choice, perplexity, sentence structure. But these tools are fundamentally fragile: each new model defeats the last detector.

Meanwhile, there is no place to go where everything you see was provably typed by a human. No feed, no platform, no protocol for it.

We think the solution isn’t better output analysis. It’s capturing the process of writing and making it verifiable.

The Approach

Speakwrite doesn’t analyze what you wrote. It restricts how you can write.

The app enforces soft keyboard only — no paste, no dictation, no autocorrect. When you publish, a SHA-256 hash of the content is signed by the iPhone’s Secure Enclave via App Attest. The post is published with tags: ["speakwrite"], and a cryptographic proof record (io.speakwrite.proof) is stored in the author’s AT Protocol repository.

Verification happens entirely on the reader’s device. Proof records are fetched from the author’s PDS (resolved via the PLC directory). The content hash is recomputed, the attestation certificate chain is validated against Apple’s Root CA, and the ECDSA signature is verified. Grey checkmark while verifying, green checkmark when the proof passes. No server in the loop.

The Protocol

Each post is published with tags: ["speakwrite"] and accompanied by a proof record (io.speakwrite.proof) stored in the author’s AT Protocol repository. No footer text appended to posts. Verification is entirely client-side — no server dependency.

The proof record

Content hash
SHA-256 of the post text. Binds the proof to the exact content. Can’t type A and publish B.
Attestation object
CBOR-encoded App Attest attestation from Apple. Contains the x5c certificate chain proving the signing key was generated on a genuine device’s Secure Enclave.
Assertion
CBOR-encoded P-256 ECDSA signature over the content hash, produced by the Secure Enclave via App Attest. Unforgeable without the hardware key.

Client-side verification

Every reader’s device independently verifies the proof. Proofs are fetched from the author’s PDS, resolved via the PLC directory:

  1. Content binding Compute SHA-256 of the post text. Compare to the proof’s contentHash.
  2. Certificate chain CBOR-decode the attestation object. Extract the x5c certificates. Validate the chain against Apple’s App Attest Root CA.
  3. Signature verification Extract the P-256 public key from the leaf certificate. CBOR-decode the assertion. Verify the ECDSA signature over the content hash.
  4. Display result Grey checkmark while verifying. Green checkmark only when all checks pass. No badge until proven.

Input restriction

The app enforces soft keyboard only — no paste, no dictation, no autocorrect. App Attest certifies the binary is unmodified, ensuring the input restriction code hasn’t been tampered with.

Why It Matters

For writers

Say “I typed this” and have it mean something cryptographically verifiable. Not a badge from a platform. Not a claim on your honor. A proof anyone can check.

For readers

A feed of posts tagged speakwrite where everything was typed by a person. Not filtered by an algorithm guessing what’s human. Filtered by cryptographic proof your device verifies independently.

For the ecosystem

An open protocol that any app can implement. Verification is pure math — SHA-256 and P-256 ECDSA. No vendor lock-in. No central authority.

For trust

One proof is weak. A corpus of proofs from the same identity, exhibiting consistent behavioral patterns over time, is strong evidence. Trust builds progressively.

Honest Assessment

It proves

A post was composed through physical typing on a genuine Apple device, with input restricted to soft keyboard only (no paste, no dictation, no autocorrect), with a SHA-256 content hash signed by the Secure Enclave via App Attest.

It doesn’t prove

That the ideas are original, that no AI was consulted, or that the author didn’t read something from another screen and retype it. It makes deception expensive — not impossible.

This honesty is a design choice, not a limitation. Speakwrite produces forensic evidence, not mathematical certainty.

Why a Native App

A web app can’t do this. Hardware attestation requires a native binary — Apple’s App Attest certifies the app hasn’t been tampered with, and the Secure Enclave holds a signing key that never leaves the silicon. No JavaScript bridge. No web wrapper. Signing happens inside the signed binary; verification happens on every reader’s device.

Why AT Protocol

Speakwrite needs three things from a social protocol: portable identity, user-owned data, and extensibility. AT Protocol provides all three.

Portable identity
Your DID (Decentralized Identifier) is yours. If you move servers, your identity, followers, and proof history move with you. No platform lock-in.
Personal Data Server
Proofs are stored as custom lexicon records (io.speakwrite.proof) on the author’s own PDS. The data lives where the author lives — not on a third-party server Speakwrite controls.
Custom lexicons
AT Protocol lets any app define new record types. Speakwrite publishes proof bundles alongside posts using a custom lexicon. Any AT Protocol client can read and verify them.
Federated verification
Proofs live on the author’s PDS, resolved via the PLC directory. Any verifier can fetch and validate them. No API key. No special access. The data is already public in the author’s repository.
Open ecosystem
AT Protocol is not one app. It’s an open network of interoperable services. Speakwrite is a native client that reads, writes, and extends the protocol — not a walled garden built on top of it.
